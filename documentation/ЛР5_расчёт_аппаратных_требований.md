# Расчёт аппаратных требований Культурного следа

Расчёт будущей полной системы (NestJS/PostgreSQL/Redis/MinIO), а не замер mock-фронтенда.
Приняты проектные допущения: 20 создателей × 2 публикации/день, 200 зрителей ×
6 отрывков/день, 8 часов активности, 365 дней/год. Публикация — 8 HTTP-запросов
(вход, список, черновик, загрузка, публикация, лента, лайк, выход);
просмотр — 2 запроса API (плитка и лента). Загрузки медиа считаются отдельно по объёму.

Nпуб = 20 × 2 = 40/день; Nhttp = 40 × 8 + 200 × 6 × 2 = 2720/день.
RPS = 2720 / (8 × 3600) = 0,0944 запроса/с.
Как в формуле 3 примера Бромберга, условная мощность — 500 запросов/с на ядро,
коэффициент резерва — 1,5. Округляем число ядер вверх до целого:
CPU = ceil(0,0944 / 500 × 1,5) = 1 ядро.
ОП = 1 × 4 = 4 ГБ. Это расчётный минимум; мощность на ядро не измерялась
нагрузочным тестом. Коэффициент пика ×5 и произвольный минимум 2 ядра не применяются.

Максимум полезных полей PostgreSQL (UTF-8 до 4 байт/символ; хеш — ASCII):
artwork_excerpts: id/creator_id 2×4, title 160×4, description 500×4,
status ENUM 4, image_url/video_url 2×500×4, DATE 4, citation_count 4,
created_at/formation_date 2×8. Итого 6676 Б/отрывок.
artwork_excerpt_likes: id/user_id/artwork_excerpt_id 3×4 = 12 Б/лайк.
users: id 4 + username 64×4 + display_name 100×4 + password_hash 255 = 915 Б.

N5 = 40 × 365 × 5 = 73 000 отрывков. При 3 лайках на отрывок и 220 пользователях,
с коэффициентом 2 для индексов и служебных данных:
VБД5 = 2 × [73 000 × (6676 + 3 × 12) + 220 × 915] / 2^30 = 0,913 ГиБ.
Прирост БД в год ≈ 0,183 ГиБ. Удалённые записи и медиа не вычитаются.
S3: среднее фото 0,3 МиБ + видео 5 МиБ = 5,3 МиБ на отрывок.
VS3год = 40 × 365 × 5,3 / 1024 = 75,566 ГиБ.
VS3пять = 73 000 × 5,3 / 1024 = 377,832 ГиБ.
Vдиск = 0,913 + 377,832 + 30 (ОС/контейнеры/журналы) = 408,745 ГиБ.
Расчётный выбор: 1 ядро, 4 ГБ ОП, SSD от 512 ГиБ; резервные копии — на отдельном носителе.
Это оценка при средних файлах. При лимитах 10 МиБ фото + 50 МиБ видео только
S3 займёт 4,177 ТиБ за 5 лет; для такого сценария хранилище нужно расширить.

Структура расчёта по примеру Бромберга: пользователи → HTTP/RPS → ядра/ОП →
размеры полей → годовой прирост → диск за пять лет. Значения рассчитаны по нашей теме.
